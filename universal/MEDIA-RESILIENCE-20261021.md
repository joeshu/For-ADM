# 客户端更新兼容性：第二轮研究（2026-10-21）

## 结论

可以减少纯构建变化造成的失效，但要区分两类变化：变量名、格式、属性写法等可验证的等价变换，可以消除匹配依赖；接口、数据契约或依赖来源变化，需要审计提示与重新核验。

本轮补上两处已通过实验复现的缺口：普通广告规则支持点属性与静态字符串括号属性互换；下载模块的响应式工厂比较改用 AST 引用结构，避免注释、空白及数值写法影响识别。两项都已接入正式脚本，未放宽域名或接口边界。

## 实验方法

基线为 `b39f0bb` 的三站已发布脚本。输入从 2026-10-21 的原版归档中选取 24 个文件：三站各包含现代/legacy 的启动模块、下载模块、主脚本，以及一份已核验结构改写最多的视图分包。这是有目的的代表样本，不是随机抽样。

对原版源码和已核验清理结果施加同一种变换，再运行正式清理器，比较完整输出 AST。比较包含辅助函数及剩余代码，忽略空白、字面量拼写、等价的静态属性访问和变量声明分组；另外检查输出语法、重复处理稳定性及拒绝边界。变换工具还用可执行的小型例子验证了 `instanceof` 相邻字符等词法边界。

共有 204 个构建变换案例及 36 个识别/契约变化案例。所有站点业务程序均未在本实验执行；真实下载行为另由 `tests/ad-media-countdown.test.mjs` 隔离测试，覆盖资源成功、旧广告状态及登录失败。这里的“完整等价”仅指该文件保留了基线的全部已核验改写，不代表网站全部广告均已覆盖，也不等于未来更新成功率。

## 本次落地的两项改进

### 1. 属性写法归一化

原结构模板记录 `store['appAdvertisements']`。压缩器改成 `store.appAdvertisements` 后，读取行为相同，但旧分词序列不同，连实际 webpack 注册标记也可能漏掉。

现在仅在匹配阶段将非可选的 `.IdentifierName` 归一化为静态字符串属性访问，保留原始源码范围，仍按原来的业务指纹、变量对应关系、冲突检测及时间/大小预算执行替换。没有把动态键、私有字段或可选链泛化为普通读取。字符串和注释中的伪代码仍不参与匹配。

### 2. 以引用结构比较工厂函数

下载模块原先比较 `body.slice(callee.start, callee.end)`。同一个 `(0, lib['KR'])` 因插入注释或数字改写而出现不同源码，就不能确认几个响应式引用来自同一工厂，整组下载改写随之退出。

现在比较标识符根、静态属性链以及是否通过 `(0, callee)` 解绑定调用；保留命名空间、成员名和调用绑定方式的区别。未知动态调用与非零序列表达式不猜测为同一工厂。六份真实现代/legacy 下载模块在注释与点属性组合变换后，通过原来的资源/错误处理行为检查。

## 仍会变化的依赖，以及下一步方向

### 框架导出别名

普通广告存在判断仍有 `P`，列表渲染入口仍有 `pI` 等依赖。它们不是业务字段，重新打包可能变化。直接将它们放宽成任意成员调用，会把未知函数当作 store 或 renderList。

下一步应先解析模块导入/导出关系，确认调用确实流向相同的 store/渲染函数，再用其数据来源匹配广告读取。另一个更集中的方向是在已验证的数据入口清理广告字段，减少每个视图渲染点都要适配的需求。不能仅凭一个 `items`、`data` 或 `list` 字段决定过滤。

### 声明布局和更大的代码重排

完整词法模板仍包含声明之间的逗号、分号及局部布局。因此，即使语义阶段能识别下载组，普通广告存在判断仍可能因声明拆分而漏掉。

下一步应把这类完整函数提升为 AST 业务契约：追踪广告集合的来源、ID 比较、返回值及局部绑定，允许声明拆分和安全重排。应先补作用域/写入检查，再扩大支持范围；本轮没有为追求案例全通过而忽略布局差异。

### 数据入口比 UI 更集中，但不能全局篡改响应

可可当前主脚本中，公共 HTTP 包装器先执行 `action`，对已识别的非 200 业务码保留拒绝分支，再将成功信封的 `data` 解包。初始化线路配置另有 `ArrayBuffer` → 解码/解密 → `JSON.parse` 的过程。这些行为分别在原版 `app.3a818181.js` 的约 611,820 和 12,472 字符处可定位。

因此不能假设所有响应都是可直接改写的 JSON，也不能清空公共请求层的全部 `data`。更稳的后续原型位置是**已核验接口成功解包后、业务消费前**：只清理确认过的广告配置及下载 `units`，沿用原错误/账户检查。当前下载辅助函数已经在局部成功回调这么做；将它扩展为通用边界前，还需要真实响应契约和不同失败响应样本。本轮没有采集用户登录响应、改动公共 HTTP 包装器或发布通用网络拦截。

## 历史源码回归

全部 1,710 份原始 JS 与 `b39f0bb` 的输出逐字比较，忽略本仓库生成的缓存修订号后全部一致；输出语法及幂等性全部通过，公告、用户/登录、媒体及 `setNetdisks` 相关受保护字面量共检查 1,842 次。没有用模拟案例的进步换取已归档版本的行为变化。结果见 [完整验证汇总](audits/media-update-resilience-validation-20261021.json)。

完整仓库回归 781 项及变换工具 2 项测试通过。真实下载行为测试包含六份现代/legacy 模块的注释与点属性组合变换。

## 持续防回退

- 将每次新原版 JS 按日期、站点、版本和 SHA-256 归档，保留历史样本。
- 正常回归验证真实模块行为；更新模拟验证能否承受构建变化。两者都不能替代另一项。
- 现有每日审计继续发现入口及动态分包变化；哈希变化即提示变化，即使探针仍可命中，也不自动提升为已核验版本。
- API、webpack 注册身份或下载公开字段变化时，保留未知代码并报告，交由契约验证。36 个边界案例用于检查这一点。
- 大小和时间预算仍生效。实验中的桌面耗时不外推为手机性能，也未完成本轮手机验收。

## 复现

仅使用仓库自带解析器，无需安装研究目录的 npm 依赖：

```sh
mkdir -p /tmp/for-adm-update-baseline
git archive b39f0bb kkapp/ad-clean.js ncat/ad-clean.js happ/ad-clean.js \
  | tar -x -C /tmp/for-adm-update-baseline
node --test research/media-resilience/updates.test.mjs
node research/media-resilience/simulate-updates.mjs \
  --runtime-dir=/tmp/for-adm-update-baseline --out=/tmp/update-before.json
node research/media-resilience/simulate-updates.mjs --out=/tmp/update-after.json
node research/media-resilience/verify-countdown.mjs \
  --baseline=/tmp/for-adm-update-baseline --out=/tmp/archive-validation.json
node scripts/check-ad-clean.mjs
```

`simulate-updates.mjs` 在实验本身失败时返回非零；支持边界仍需查看各场景的 `equivalent/misses/declined`，不能只看进程退出码。
