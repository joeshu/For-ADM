# 更新后去广告兼容性研究（2026-10-18）

## 结论

可以显著减少这类更新造成的失效。此次三站更新的已核验广告逻辑，在忽略混淆变量名后，结构保持一致；规则对构建身份的依赖，比广告业务逻辑本身的变化更容易造成失效。

适合的方向是：保留已验证的精确规则，增加受业务语义和变量引用关系约束的共享结构适配。不能直接把所有 `_0x...` 改成通配正则，也不能保证以后所有版本永久兼容。

## 实际比较了什么

从仍可访问的旧版本 URL 获取三个站点各 74 个相关 JS 模块，共 222 个。旧源码逐一通过原来的每站 94 组完整指纹和精确出现次数检查，保证比较对象确实支持原规则。

新版覆盖每站主脚本和其动态加载映射中的 248 个 JS 文件，共扫描 744 个文件；不含 HTML 单独引入的 vendor 第三方库。与新版人工适配清单独立比较：匹配原型只使用旧版动作，未使用新版变量名、哈希、文件路径或新版替换对来学习匹配方式。新版清单仅作为事后对照。

| 站点 | 对比版本 | 新版已核验改写位置 | 旧版结构可识别 | 可独立生成正确替换 | 超出对照清单的可改写候选 |
| --- | --- | --- | --- | --- | --- |
| 可可影视 | 2.5.14 → 2.5.15 | 208 | 208 | 204 | 0 |
| 网飞猫 | 2.5.29 → 2.5.30 | 208 | 208 | 204 | 0 |
| 好好看 | 2.5.22 → 2.5.23 | 208 | 208 | 204 | 0 |

“位置”指真实源码中的一次出现；同一替换模板可能出现多次，因此不是文件数或规则组数。204/208 约为 98.1%，只描述此次版本对照，不能作为未来成功率。

可改写候选的全部组合未发生重叠/替换冲突，生成的源码通过 Node JS 语法检查。这里没有执行网站程序、注入并验证辅助函数，也没有进行浏览器行为或手机验收。

原型有 7 项边界测试：变量重命名、空白/注释、字符串转义、数字写法、重复变量引用、字符串/注释/模板/正则中的伪代码、业务字段或操作改变、未知外部变量、冲突改写等。报告中的“额外候选 0”仅表示在这批源码上没有超出既有核验位置，不能证明任意未来源码均不会误匹配。

## 具体发现

### 1. 构建信息变化，业务结构仍可识别

例如已核验横幅逻辑具有以下结构，变化的是两处变量名：

```js
// 旧版某分包
_0x451760 = _0x118a69['appAdvertisements']
// 新版对应逻辑（分包文件也已变化）
_0x108924 = _0x5fd66d['appAdvertisements']
```

`getAdvertiseById`、`appAdvertisements`、`ads.find`、`VOD_START`、`VOD_PAUSE`、`units.splash/video/dhz` 和 `/v2/config/units.capi` 等业务线索仍存在。仅引用变量名的精确字符串规则会失效，识别完整表达式及其变量对应关系则能够继续定位。

每站可独立生成替换的 186 条旧替换对可归并为 43 种词法结构，说明共享结构适配比继续逐版登记全部变量更值得研究。

### 2. 文件名里的哈希不能当作内容保证

每站有 13 个旧、新版本共有的分包文件名，包括相同的哈希后缀，但 13 个文件的源码字节均不同。版本目录不同，实际内容也不同。

因此，“相同哈希文件一定没变”不成立。需要继续使用自身适配版本产生缓存参数，并检查实际源码结构。只放宽版本号、只匹配文件哈希、或只刷新浏览器缓存，都不能完成长期适配。

### 3. 下载页不能逐条盲目改变量

每站剩余 4 个片段位于现代/legacy 下载页的初始化和广告分发函数。它们本身的旧版结构均能在新版识别，但替换代码需要使用片段外的倒计时引用和清理函数。

例如一个替换要执行 `countdownRef.value = 0`，原待替换函数中却不含这个引用，必须从其他已核验结构取得对应变量。逐条替换变量可能留下旧变量名，语法仍通过，运行时才报错。

研究原型明确拒绝生成这些替换。正式实现需要作用域和跨规则的绑定验证；当前已发布精确规则继续负责这部分行为。

### 4. 混淆变量不是唯一易变信息

Webpack 数字模块 ID、`so` 等导出别名、`pI` 等框架导出别名、现代/legacy 编译形式、点属性与括号属性写法，也可能改变。此次原型保持了这些代码结构，不能据此推断另一种打包器或压缩策略仍会兼容。

另外，原型对重复标识符保持一致映射，但没有进行完整的 JavaScript 作用域/数据流分析；对复杂作用域变化，仍须由正式语义分析或拒绝改写保护。

## 建议的实现顺序

1. **先消除无必要的版本绑定。** HTML 缓存更新采用已登记站点、站点品牌/应用壳特征和已支持 app 脚本路径族，不依赖某一个具体 app 哈希。保留域名、端口、页面路径和供应商脚本边界。
2. **为稳定的广告读取逻辑增加结构后备规则。** 先支持广告 getter、横幅读取和已确认的卡片数组入口。按完整表达式/函数确认字段、操作与变量对应关系；候选冲突或业务逻辑改变时保持响应，并写诊断记录。不要任意把包含 `ads` 的函数置空。
3. **配置清理依业务来源定位。** 用 `/v2/config/units.capi` 对应的实际请求函数及返回契约定位广告配置，逐步摆脱数字模块 ID 和导出别名；公告、初始化、账户和真实资源必须分开保护。下载页需先补跨函数绑定验证。
4. **让审计主动发现新版本。** 从当前 HTML 和动态加载映射发现新文件，运行结构探针，检查缺失、冲突和新结构；不能只继续抓取旧目录。自动发现变化不等于自动把未经行为验证的规则发布。
5. **用手机验证后再启用后备规则。** 先诊断模式记录候选，不改响应；验证首页、影片详情、选集、播放、下载和登录后逐步启用。每个未知结构独立保留，避免一个小变化让整个大替换组全部失效。

接口 JSON 层清理也值得考虑，但本次只分析公开 JS，没有获取真实 API 响应。源码可见请求签名和共享请求封装，不能仅凭接口名称就假定可直接清空 JSON 或拒绝请求；需要实际响应结构与调用契约作为依据。

## 原型状态与限制

原型位于 `research/media-resilience/`，仍只用于离线比较。后续正式接入采用进一步收窄的 39 种结构模板和运行保护，参见 [正式说明](MEDIA-STRUCTURAL.md)；这里保留的是较宽研究原型的数据，不能混用为正式方案的覆盖率。

原型依赖 Acorn 分词。当前 Node 环境每文件分词及索引构建中位数约 2.5–2.8 ms，结构匹配中位数约 1.5 ms；部分较大文件耗时超过 100 ms，测量也包含运行时开销。该测量不能外推手机性能；正式方案应先做业务特征预筛选，避免所有分包均执行完整解析，并测量 QX 时间和内存限制。

三站使用相近架构，此次数据仅覆盖各站一组相邻版本。它证明了本次失效具有可避免的构建绑定因素，不能证明架构重写、接口契约变化、字符串加密或新广告形态也能自动处理。
