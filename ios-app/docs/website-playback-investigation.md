- 默认线路失败后应按同一影片、同一集继续检查备用线路；不只检查第一条。

- 原始详情没有可靠的统一 `channelId`，不应从模糊的题材标签猜测“电影”。
- 成功清单应继续交给原生 AVPlayer 验证时间推进；HTTP/HLS 成功本身没有证明解码和全部分片可用。

## 电影猎手

每片最多检查三条对应选集线路。原版 `playerService` 的解析判断为：

1. 已有 `parseUrl` 时直接使用。
2. 优先读取线路、再读取分集的 `need_to_parse / player_need_to_parse`，兼容布尔值和字符串 `1 / true`。
3. 这些字段不存在时按 `!episode.ready_to_play` 判断，**不能将字段缺失当作不需要解析**。

此前的首页样本直接取 `play_url` 因而不完整。本次真实调用 `/movie_addr/parse_url` 8 次并取得地址，
不再只是从源码推测参数结构。

| 影片 ID | 分集标题 | 可用 HLS 线路 / 分集 ID | 可用 MP4 线路 / 分集 ID |
| --- | --- | --- | --- |
| `nrLxl` | 正片 | `cloudflare` / `196849326` | `bytedance` / `202942809` |
| `6Xnqz` | 正片 | `cloudflare` / `204581626` | `bytedance` / `204536061` |
| `Gv3jK` | 抢先版（其他线路标题为正片） | `cloudflare` / `205379049` | `bytedance` / `197740035` |

`cloudflare` 的页面名称为“官方线路-C”，三个样本解析后均取得 `lf1.wikjdd.cn` 的有效 HLS 清单。
`bytedance` 的页面名称为“高清-官方线路B”，返回无 `.mp4` 后缀的 HTTPS URL；
不能按文件名后缀认定不是视频。三个样本都取得了 HTTP 200、`video/mp4` 的 HEAD 响应。
`Dong`（高清-官方线路D）样本仍返回 403。

### Referer 差异

`bytedance` 的三个样本在附加本站 Referer 时均为 403；使用不带 Referer 的请求则得到 MP4 HEAD 200。
原站 HTML 设置了 `referrer=no-referrer`。因此给所有来源的媒体请求强制添加站点 Referer，
会制造原站请求中不存在的头部并导致这些地址被误判失效。
移动 UA 与原始默认请求的对比结果逐条列在报告中。

原生接入应保留线路明确提供的 `player_headers / player_user_agent`；
对于没有指定 Referer 的电影猎手线路，沿用其不发送 Referer 的行为。
这些结果不能扩展成“对所有网站都删除 Referer”，因为其他站点可能明确要求该头部。

## 当前结论与验收范围

三站的元数据、选集、地址获取流程和部分备用媒体传输均已有实测依据，具备编写独立原生适配器的基础。
接口返回的部分默认线路仍不可用，接入时必须保留取消、同集回退、错误分类和可配置请求头。
本次所有媒体项的 `decodedPlaybackVerified` 均为 `false`；发行前仍须用 iOS 模拟器或真机验证
播放器加载、时间推进、切集、返回和切换来源后的资源释放。

## 全线路复核

新增 `tools/dyls-lines-probe.mjs` 使用 App 相同客户端与媒体检查器，逐条检查一部电影和一部剧集的全部来源。结果保存于 [全线路报告](dyls-lines-probe.json)：蜘蛛侠崭新之日：16 条来源，10 条本次媒体传输通过；嫁金钗：18 条来源，13 条本次媒体传输通过。失败仅表示当前网络和选集样本的结果，不据此隐藏、删除或永久禁用该来源。所有原站来源仍可手动选择；单次自动回退的五条预算不影响手动选择第六条及以后的线路。该行为有第十三条线路选择的单元测试覆盖。
